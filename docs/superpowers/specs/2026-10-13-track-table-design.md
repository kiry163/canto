# 曲目列表：统一列模型与表头（设计）

**日期：** 2026-10-13
**状态：** 待评审
**取代：** 无（但改写 `README.md` 已知限制里三条与列表列有关的条款，见文末「与旧条款的关系」）

## 背景与目标

曲目行的拼装现在散在 8 处绘制点、没有任何共用函数，重复分三类（都实测过行号）：

- **歌曲行 3 套并存**：`content.rs:258` `draw_songs`（时间 + 音质 + 体积 + 已缓存 + 已丢失）、
  `content.rs:209` `draw_history`（标题—歌手 + 右侧「时间 · 来源」）、`overlay.rs:326` `draw_queue`
  （时间 + 标题—歌手）——各自写一遍 `♪` 标记、`{title} — {singers}` 与 `List` 外壳。
- **歌单行公式抄 4 遍**：`{:>5}  {name}` 出现在 `content.rs:42`、`content.rs:66`、
  `overlay.rs:29`、`overlay.rs:49`；其中 `overlay.rs:27` 把「7 列缩进」硬编码成字面量
  `       新建…`。
- **样板重复**：`List::new(..).block(..).highlight_style(highlight()).highlight_symbol("▶ ")`
  7 次；`std::mem::take(&mut ..state)` / 回写 2 次（绕借用检查）；空态
  `Paragraph(DarkGray + Center + panel_block)` 3 次。

同时没有表头、没有列模型、没有列宽与截断（曲目行的宽度全是内联 `{:>5}` / `{:<9}` / `{:>7}`
加一个固定 7 列的缓存槽，然后交给 ratatui 硬裁），于是三处「列在撒谎」：

1. **本地歌的档位列**：`Song.sizes` 全 0 → `sizes.at_or_below()` 退回配置下限（`model.rs:157`），
   于是一个本地 FLAC 文件在列表里显示 `MP3 128k`。
2. **已下载的歌**：下载目录里明明躺着一份 31MB 的 FLAC，行里仍按配置下限写 `MP3 128k 4.2MB`
   ——「是否已下载」在界面上根本看不见（只有下载那一刻的状态行一句 `已存在：…`）。
3. **历史与本地歌单的行**：时长 `--:--`、档位占位、体积 `—`（历史是因为记录里没存，
   本地歌单是因为条目快照只存 mid/标题/歌手）。

目标：

- **一处列模型**：列的表头、宽度、对齐、取值写在一处；**一处画行**、**一处画表头**。
- **所有曲目列表都带表头**（收藏 / 歌单曲目 / 搜索 / 本地曲库 / 本地歌单曲目 / 历史 / 队列浮层）。
- **网络歌曲显示「是否缓存」与「是否已下载」**，两个标记列 + 表头当图例。
- 顺手消掉上面那三处撒谎：本地歌报自己的容器与真实大小；历史把手里本来就有的时长/体积落盘；
  本地歌单曲目按 mid 查曲库补齐。

## 非目标（YAGNI，明确不做）

- **不换 ratatui 的 `Table`**：保持 `List` + `ListState`（见「决策记录」第 2 条）。
- **列不可配置**：不加 `[ui]` 配置段、不落盘列顺序/列宽，不记「上次怎么排的」。
- **不做排序、不做手工调列宽、不做横向滚动**：宽度只有「按窗口分配 + 让位」两件事。
- **不动首页网格与帮助浮层的排版**：它们不是曲目列表（帮助浮层那个 `Row` 是自建枚举，
  与本次的列模型无关）。
- **不动键位**：本次一个按键都不加、不改。
- **不给歌单列表（QQ / 本地 / 两个选择框）上表头**：它们不是曲目列表；本次只把那 4 份
  重复公式合成 1 份。

## 决策记录

| 决定 | 取值 | 为什么 |
|---|---|---|
| 统一的边界 | **行级**：列模型 + 共用画行 + 表头；`List` 壳、空态、选中态仍各屏自己写 | 重复的大头是行格式（3 套）与歌单行公式（4 份），不是那 7 份 4 行的外壳；先收大头，外壳合并留给「下次又要加一屏」时 |
| 表格实现 | **自绘列模型**，继续用 ratatui 的 `List` | `ListState` 上钉着选中/翻页/筛选与 8 个 `ListView`、一批 `frame_flat` 断言；换 `TableState` 要穿透这些，而我们自己那 60–80 行宽度分配与库的 `ColumnConstraints` 收益相当。仓库里也从没用过 `Table` |
| 列顺序 | `标记 · 标题 · 歌手 · 时长 · 音质 · 体积 · 缓存 · 下载 ·（备注）` | 最常读的（标题、歌手）放最左；元信息靠右对齐成一排；窄屏先被截的是尾部元信息，不会把歌名切掉 |
| 标题与歌手 | **两列**，不再拼成 `标题 — 歌手` | 拼成一列时两段长度互相影响，无法各自截断、也无法对齐；拆开后「歌手」这一列在两行之间才是可比的 |
| 缓存 / 下载 | **两个标记列**（`●` / `↓`，表头写「缓存」「下载」当图例） | 文字列（`已缓存`/`已下载`）两列要 ~16 列宽，60 列窗口下标题只剩 ~20 列；一个字符的标记 + 表头图例同样自解释。两列分开是为了能同时表达「既缓存又下载」 |
| 音质 / 体积的口径 | **本地已有那份就报那一份**：缓存 > 下载 > 曲库文件 > 按配置下限预估 | 行里那一列是「重听这一首会用哪一份」。缓存那份的档位能从文件名精确读出；下载与曲库文件读不出码率，**只报容器**（`.flac`→`FLAC`、`.m4a`→`M4A`、`.mp3`→`MP3`），不猜 128/320 |
| 本地的容器 | 取路径扩展名（大写） | 顺手修掉「本地 FLAC 显示 MP3 128k」；不需要新数据源 |
| 本地文件的大小 | `library::Entry.size`（**索引里本来就有**）→ 经 `Song.local_bytes` 带到行上 | 曲库扫描本来就 stat 过（mtime + size 用来做增量判断），只是 `entry_to_song` 丢掉了 |
| 历史的时长/音质/体积 | **落盘补两个字段**（`duration_secs` + `sizes`） | `record_history` 手里的 `Song` 本来就是完整的，只是没抄；`refresh_history_view` 再还原回 `Song`，所以**从历史重播不会把数据写丢** |
| 本地歌单曲目的时长/体积 | 按 mid 查当前曲库补齐（那张屏已经每行查一次曲库判「已丢失」，改成一次建表） | 快照刻意只存 mid/标题/歌手（文件移走也在），但文件还在时没道理显示 `--:--` |
| 列集 | **按屏声明**，沿用「没有的字段就不画」 | 队列浮层最宽 72 列、且没有「来源」那一栏；本地曲库那几屏的歌不经过缓存/下载 |
| 让位顺序 | `备注 → 体积 → 音质 → 时长 → 歌手`；`标记`/`标题`/`缓存`/`下载` **永不撤** | 标记列是这次的目的；标题是主体；前四个元信息里「体积」是最接近多余的（它是预估），备注本来就只在两屏出现 |
| 表头何时画 | 可用高 ≥ 6 时画一行（固定不滚），否则把那一行还给数据 | 矮屏里一行数据比一行表头值钱；尺寸矩阵里最紧的一档是窗口 20 行（内容区 15 行），仍然画 |
| 表头缩进 | 前缀 2 空格，与 `highlight_symbol("▶ ")` 同宽 | `List` 会给**每一行**留选中符号那 2 列；表头不缩进就会整体左移 2 列，列位对不上 |

## 1. 列模型

新建 `src/tui/draw/rows.rs`（约 200 行含单测）。它是纯函数集合，不认识 `App`：

```rust
/// 一列读哪个字段。
pub(super) enum Field { Marker, Title, Singers, Duration, Tier, Size, Cached, Downloaded, Note }

/// 一列的排布：表头文字（标记/备注两列的表头是空串）、宽度、对齐。
pub(super) struct Column {
    pub field: Field,
    pub title: &'static str,
    pub width: Width,
    pub align: Align,
}

pub(super) enum Width { Fixed(u16), Fill { min: u16 } }

/// 一行能填的数据。屏各自填能填的：填不出的留 `None`，那一格就渲染占位符。
pub(super) struct Row<'a> {
    pub playing: bool,              // ♪
    pub title: &'a str,
    pub singers: &'a str,
    pub duration: Option<u64>,      // 秒；None → `--:--`
    pub tier: Option<Cow<'a, str>>, // 音质或容器
    pub size: Option<u64>,          // 字节；None → `—`
    pub cached: bool,
    pub downloaded: bool,
    pub note: Option<&'a str>,
}
```

三个函数（都能单测）：

- `fit(columns, width) -> Vec<Column>`：① 算 `Fixed` 总和 + 分隔（列数 − 1 个空格），`Fill` 列各先记它的
  `min`；② 超出宽度就按让位顺序**撤列**（连同它那一个分隔），撤到装得下或只剩不可撤的列；③ 剩下的余量
  在 `Fill` 列之间等分。
- `header(columns, indent) -> Line`：`DarkGray` 一行，每格按列宽对齐（`时长`/`体积` 右对齐、
  `缓存`/`下载` 居中、其余左对齐）。
- `line(columns, row, indent) -> Line`：每格取值 → 补齐到列宽（中文按显示宽度，`truncate_to_cols`
  截断并补 `…`）→ 列间 1 个空格。`标题`/`歌手` 也补到各自宽度，后面的列才不会左右抖。

**宽度常量**（`Fixed`）：`标记 1`、`时长 5`、`音质 8`、`体积 7`、`缓存 4`、`下载 4`；
`Fill`：`标题 { min: 8 }`、`歌手 { min: 8 }`、`备注 { min: 12 }` —— `备注` 的 `min` 是刻意的：
分不到 12 列时一句「3 小时前 · 来自《…》」只会被截成半截，不如按让位顺序出局。

**颜色**：`●` 绿（沿用今天「已缓存」那一档）、`↓` 青、表头与备注 `DarkGray`、
`（已丢失）` `DarkGray`（今天就是）；标题/歌手/时长/音质/体积用默认前景色。

**60 列窗口的算术**（列数最多的历史屏，9 列）：定宽 `1+5+8+7+4+4 = 29`，分隔 8 列，
三个 `Fill` 的 `min` 合计 `8+8+12 = 28` → 共 65 > 60；按让位顺序撤掉 `备注`（12 列 + 它那一个分隔）后
剩 8 列、7 个分隔、两个 `Fill`：`29 + 16 + 7 = 52`，余量 8 在 `标题`/`歌手` 之间等分 ——
**标题 12、歌手 12，合计正好 60**。所以最小窗口下被撤的只有 `备注`，其余 8 列全在。

`truncate_to_cols`（现在住在 `draw/status.rs:26`，私有）挪到 `draw/mod.rs`，与
`format_size` / `format_duration` 放在一起——它们都是「画行小工具」；`status.rs` 与
`rows.rs` 都用它，它的中文双宽与 `…` 收尾有现成测试。

## 2. 各屏列集

| 屏 / 浮层 | 列集 |
|---|---|
| 收藏 · 歌单曲目 · 搜索（`draw_songs`） | 标记 标题 歌手 时长 音质 体积 缓存 下载 |
| 本地曲库（`draw_songs`） | 标记 标题 歌手 时长 音质 体积 |
| 本地歌单 › 曲目（`draw_songs`） | 标记 标题 歌手 时长 音质 体积 备注 |
| 历史（`draw_history`） | 标记 标题 歌手 时长 音质 体积 缓存 下载 备注 |
| 队列浮层（`draw_queue`） | 标记 标题 歌手 时长 缓存 下载 |

- 本地曲库那两屏不带 `缓存`/`下载`：本地歌不经过播放缓存，也不叫「下载」——整列恒空只是噪声。
- 历史带 `缓存`/`下载`：它存的也是 `Song`（有 mid），本地条目那两格空。
- `备注`：历史填 `{相对时间} · 来自《{来源}》`（沿用今天右侧那段文字，`state.rs:2226` 现成），
  本地歌单填 `（已丢失）`。
- 标记列的 `♪` 与选中符号 `▶ ` 是两回事：`♪` 是「正在播」（按 mid 比对，`now_playing_mid()`），
  `▶ ` 是光标（`List` 的 `highlight_symbol`，不动）。
- 队列浮层里 `♪` 按**队列下标**（今天就是 `index == playing`），不按 mid——队列里可以有同一首
  出现两次，按 mid 会两行都标。

## 3. 数据来源与刷新

| 事实 | 数据源 | 键 | 刷新时机 | 代价 |
|---|---|---|---|---|
| `●` 与「音质/体积（缓存）」 | `App.cached: HashMap<String,(Quality,u64)>`（**已有**，`state.rs:767`） | `mid` | 启动扫一遍 + 每帧排空音频线程的升级队列（`state.rs:2452`，现成） | O(1) |
| `↓` 与「音质/体积（下载）」 | **新增** `App.downloads: HashMap<String,(String 容器, u64 字节)>`，由 `read_dir(下载目录)` 建 | `download::file_stem(song)`（`歌手 - 标题`，与下载同名规则**同一份函数**，改成 `pub(crate)`） | ① 启动一次 ② 每次下载成功后一次 ③ 按 `r` 重扫曲库时顺带一次 | 一次 `read_dir`；查是 O(1) |
| 本地歌的容器/大小 | `library::Entry.size`（**已经在索引里**）→ `Song.local_bytes` | `mid` / 路径 | 随曲库扫描（现成机制） | O(1) |
| 历史的时长/体积 | `history::Entry.duration_secs` + `.sizes`（**新增两个字段**，`#[serde(default)]`） | — | 起播时 `record_history` 抄手里那份 `Song` | — |

口径：

- **同一 stem 有多份**（mp3 + flac，或 128 + 320 两份 mp3）：取**档位最高**那份的容器与大小。
  `↓` 是一个布尔标记，不区分两份。
- **撞名**（同歌手同标题的不同歌）：两行都会标 `↓`。这与今天下载时「文件已存在就跳过」
  是同一个口径（拿到的还是同一份文件），所以不新增谎——但要写进已知限制。
- **`↓` 与本地曲库同源**：下载目录默认就是曲库的扫描根（`config.rs:196`），所以同一首歌会有
  两行（收藏里一行标 `↓`，`5` 里一行）。这是既有行为，`↓` 只是把这个关系显出来。
- **历史的老条目**：升级前写的记录没有那两个字段，读回来是 `0` → 时长 `--:--`、体积 `—`；
  从别的列表（收藏/搜索/队列）再播它一次就补上。**从历史重播不会丢**：还原出来的 `Song`
  带着字段，写新记录时照抄。
- **本地歌单曲目**：那张屏按 mid 建一次 `曲库 → (容器, 字节, 时长)` 表（把今天每行的
  `self.library.iter().any(..)` 换成查表，顺带把 O(行×曲库) 降成 O(曲库)），查得到就补齐
  时长/容器/大小；查不到 = 已丢失 → `--:--`/`—` + 备注「（已丢失）」。

## 4. 绘制接线

- `rows::group(columns, area) -> (header: Option<Rect>, list: Rect)`：可用高 ≥ 6 才切出表头那一行。
  切分在各屏自己的入口做（`draw_songs` / `draw_history` / `draw_queue`），**`draw::layout` 不动**
  ——表头是「列表」的事，不是「内容区」的事（首页网格与频谱区都不该受影响）。
- 队列浮层：`height = items.len() + 2` 变 `+ 3`（表头那一行）；宽度仍是
  `area.width - 8` 与 72 的较小值。
- 表头样式：`DarkGray`（与「来源 / 备注」这类次要文字同一档）。
- 搜索屏：输入行 + 表头 + 结果，三段自上而下（输入行今天已单独占一行）。

## 5. 退化与错误处理

| 情形 | 行为 |
|---|---|
| 窗口 60×15（最小） | 内容区 10 行 ≥ 6 → 画表头；60 列下撤 `备注`，其余列全在 |
| 内容区 < 6 行 | 不画表头，整块给列表 |
| 标题 / 歌手超长 | 按显示宽度截断 + `…`（中文双宽算对；`truncate_to_cols` 现成） |
| 时长未知（本地读不出 / 老历史条目 / 已丢失的本地歌单条目） | `--:--`（不写 `00:00`） |
| 体积未知（QQ 接口没报 / 没有本地副本且接口没报） | `—` |
| 音质未知（本地歌路径没有扩展名） | `—` |
| 空列表 | 各屏自己的空态文案不变（本次只把 3 处同款配方收成 1 个 helper） |
| 撤到只剩不可撤的列仍超宽 | 不会发生：窗口 < 60×15 只显示一行「终端太小」，而 60 列下最长的历史屏算下来正好 60 列；`Fill` 列压到 `min` 就停，再超也只能由 ratatui 裁尾（留一条兜底，不写额外逻辑） |
| 队列浮层的**内**宽比内容区还小 | 浮层宽 = `min(内容区宽 − 8, 72)`，60 列窗口下是 52；它的列集（6 列）定宽 `1+5+4+4 = 14` + 分隔 5 + 两个 `Fill` 的 `min` 16 = 35 ≤ 52，余量 17 给标题/歌手 —— 装得下，不需要撤列 |
| 一台机器上同时有缓存与下载两份 | `●` 与 `↓` 都标；音质/体积报**缓存**那份（播放也是先命中缓存） |

## 8. 风险与已知限制

- **表头占一行内容**：矮屏（内容区 < 6）不画来兜住；其余情况下每屏少一行数据。
  既有的一批「第几行是什么」的断言要逐条重算，这是本次最容易漏的地方。
- **`Song.local_bytes` 是新字段**：QQ 侧的构造点与测试辅助要一起填 0（机械改动，
  但漏一处就是编译错误，反而不会静默）。
- **`↓` 是按文件名认的**：同歌手同标题的不同歌会互相标上；外部手工拷进下载目录的文件也会被
  认作「已下载」（今天下载时就会把它当「已存在」跳过，口径一致）。写进已知限制。
- **`↓` 的档位/体积读不出码率**：mp3 只写容器 `MP3`，不比缓存那份精确（缓存文件名里有档位）。
  写进已知限制。
- **历史的老条目**永远显示 `--:--`/`—`，直到它从别的列表被播一次。写进已知限制。
- **60 列下历史那行是 58/60 列**：几乎没有余量，以后再加一列就必须动让位顺序（记在这里，
  免得下次以为是随手能加的）。
- **缓存那份与下载那份同时存在**时音质/体积报缓存的（播放也是先命中缓存），`↓` 只表「磁盘上
  还有一份」。这是刻意的：两列各自回答自己的问题，不在格里塞复合状态。
