# canto 实现与设计说明

README 只讲「怎么用」，这里讲「怎么做、为什么这么做、实测到什么」。界面重构那一轮的决策记录
（分节确认的过程、放弃的方案、验证方式）在 `superpowers/specs/2026-10-11-tui-redesign-design.md`，
这里只收当前有效的结论。

## 播放与缓存

播放是**流式**的：`vkey` 取到 CDN 地址后开一条 HTTP 流，边下边解码出声，不需要先落盘，
所以起播几乎是瞬时的。正常播放是「一次请求顺序读到底」；往回拖进度、或往前跳超过 4 MiB
才重开一次 `Range: bytes=N-` 请求（往前走小距离就直接读掉，省一次连接）。

在此之上加了一层**磁盘缓存**（`~/.cache/canto`，上限 `cache_mb`）：

- 文件名是 `<mid>.<档位>.<扩展名>`（mid 全局唯一、不会过期；vkey 会过期所以不能进键。
  档位写进名字是为了算「这份是什么档位」时不用猜——`320` 与 `128` 都是 `.mp3`）
- 边播边写 `.part`，**只有从头顺序听完**（写出去的部分连成一片、并且真的铺到文件尾）才
  改名成正式缓存；中途跳走留下的洞不算数，半截文件直接删掉
- 再次听同一首歌：命中完整缓存就完全不碰网络（连取流请求都省了），拖动进度也是瞬时的
- **列表里有「已缓存」标记**（绿色），一眼知道哪些歌重听不用网络；已缓存那行显示的
  就是**缓存里那份**的档位与真实大小（跟播放条一致），没缓存的按配置下限算
- **下载会先看缓存**：已经有完整的一份就直接复制到下载目录（一个字节都不走网络），
  档位以缓存里那份为准；歌词同样优先用下面这份缓存
- 超出上限时按「最久没听的先删」清理；`cache_mb = 0` 关掉缓存（顺手把存货也清空）

**歌词也缓存**（`~/.cache/canto/lyrics/<mid>.lrc`，跟歌曲分开两份）：播放与下载都先查它，
命中就省一次请求；「这首没有歌词」也记一笔（空文件当记号），免得反复为空结果发请求。
歌词体积很小，不计入 `cache_mb` 上限，但 `cache_mb = 0` 时一起关掉。

注意：缓存**只有你听完的歌**才有，所以它不等于离线模式——没听过的歌仍然要联网。

## 音质档位（实测，2026-10-09）

同一首歌在 CDN 上有一组候选文件。`canto` 按「立体声优先、音质降级」排队，逐个**真去开**，
第一个能解码的胜出——因为服务端对不存在/无版权的文件**也会**返回 `purl` + `vkey`，
只有真去取才 404（`file not exist`），光看接口结果判断不出来。

| 前缀 | 实测规格 | 体积（4 分钟量级） | 用途 |
|---|---|---|---|
| `AI00` | flac 192kHz/24bit 立体声 | ~150MB | 母带，仅 `quality = "hires"` |
| `F000` | flac 44.1k/16bit 立体声（个别 48k/24bit） | ~25MB | **默认首选** |
| `Q000` | flac 44.1k/16bit 立体声 | ~25MB | 默认次选 |
| `M800` | mp3 320k 立体声 | ~9MB | 无损不可用时 |
| `M500` | mp3 128k 立体声 | ~3.5MB | 兜底 |
| `Q001` | flac 44.1k/16bit **6 声道** | ~62MB | 5.1 环绕，排在 mp3 之后 |
| `O801` | vorbis 44.1k **4 声道** | ~19MB | 环绕，最后兜底 |

`quality` 的语义是「从这一档往下找」：`hires`（母带）→ `flac`（默认）→ `320` → `128`。
环绕声版本排在立体声之后，是因为它们只会经过 rodio 的降混，白白多花带宽。

## 登录二维码（实测，2026-10-11）

`ptqrshow` 返回一张 **1-bit 灰度 PNG，111×111 像素**：符号本体是 **33×33 模块**（QR version 4），
**每模块 3 像素**，四周 **2 模块静区**。逐像素往终端里画等于把 9 份重复的像素都搬上屏幕
（一个字符格 = 1 像素宽 × 2 像素高，于是要 112 列 × 61 行），普通终端根本装不下。

所以 `qr.rs` 先把图**还原成模块网格**再画：

- 深色像素的包围盒 = 码体（静区是白的，不算）；码体内**最短的深色游程 = 一个模块的像素数**
  （时序线必然是 1 模块宽的黑白交替，这个下界一定取得到）；
- 校验「宽高相等 + 模块数是奇数且在 21..177 + 四边静区是同样的整数个模块」都成立才认，
  否则退回逐像素（图被缩放过、带抗锯齿时的保底，画出来跟以前一样大）；
- 一个模块占**一个字符格宽**，纵向两个模块拼一格（`▀` / `▄` / `█` / 空，深色留空 = 用终端
  深色背景）。33 模块的码只占 **37 列 × 19 行**；
- 终端够大时按 **1 / 2 / 4 倍**放大（每模块 `scale`×`scale` 像素）；奇数倍会让模块跨在半格上
  对不齐，所以只认 1 与偶数。最低要求因此降到 **38 列 × 23 行**（原来要 112×61）。

实测：80×24 的终端里画出的字符块**逐格反转回来与源 PNG 的模块网格完全一致**（37×37 全对）。

## 全局快捷键（实测，2026-10-12）

canto 常停在某个 pane 里、甚至被别的窗口盖住，所以「切歌 / 调音量」不该要求先切回终端。七个动作
（播放暂停、上下一首、音量 ±5、开/关桌面歌词窗口、切桌面歌词的锁定/解锁）注册成**系统级**热键，
跟界面上的 `Space` / `n` / `b` / `+` / `-` 走**同一条派发路径**（`App::apply`）——两套输入、一套语义。

平台差异是这个功能的全部难点，因为 crate（`global-hotkey`）只负责「注册」：

| | Windows | macOS |
|---|---|---|
| 事件怎么来 | `RegisterHotKey(hwnd, …)` 把 `WM_HOTKEY` **投递给建窗口那个线程** | `RegisterEventHotKey` 把热键事件送进 **Carbon 的事件队列**（`InstallEventHandler(GetApplicationEventTarget(), …)` 收）——**不走 CFRunLoop 的 source** |
| crate 做了什么 | 建一个隐藏窗口 + 自己的 WndProc；注册时带 `MOD_NOREPEAT`（所以按住不连发） | 注册 Carbon 热键 + 装事件处理器 |
| 我们得做什么 | 自备专用线程：建窗口 → 逐条注册 → `GetMessageW` / `DispatchMessageW` 循环；`Drop` 时 `PostThreadMessageW(WM_QUIT)` 再 `join` | 主线程建 manager（`tui::run` 本来就在主线程），UI 循环每轮把队列里那两类热键事件**拉空并派发**（`ReceiveNextEvent` + `SendEventToEventTarget`）——**不拉就没事件**，延迟上限就是 tick（150ms） |
| 其它平台 | Linux / Wayland 不注册；启动时说一句「此平台暂不支持全局热键」，其余功能照常 | |

几个刻意的地方：

- **事件出来是 `keys::Action`**，不是另一套动作枚举：不会出现「界面能暂停、热键走另一条逻辑」的
  漂移。音量步长也跟界面一致（±5，`player.rs` 里夹在 0–100）。
- **只在主界面派发**（`App::dispatch_hotkey`）：登录屏没有播放可控，按了就当没按。热键也不走
  `apply_login`——cookie、二维码跟播放控制不是一码事。
- **必须有修饰键**：crate 允许裸键（`space`），但那等于让 canto 抢走全局空格。配置阶段就拒掉：
  清成 `""` + 一条点名字段的警告。于是全程只有一条不变式：**非空 = 合法 = 会被注册**。
- **逐条报失败**：一条组合被别的程序占了，不该拖累其余六条。状态行右侧说一句（一条时点名、多条
  时报个数），原因（`HotKey already registered: …`）进 `canto.log`。
- **`install` 在 `tui::run` 里、不在 `App::new` 里**：`test_app()` 会走 `App::new`，真注册系统热键
  既污染开发机、又会抢走使用者的按键。
- **默认不碰媒体键**：七个动作的默认组合都是普通组合键，所以正常情况下不弹授权框。但配置里
  如果自己写媒体键名（`mediaplaypause` 之类），macOS 上 crate 会走 CGEventTap、可能弹一次
  辅助功能授权——所以模板里写明了别那么写（Windows 上媒体键就是普通注册，没这个问题）。
- **macOS：热键事件得自己从队列里拉**（2026-10-12 在 macOS 15.5 / x86_64 上实测）：Carbon 的热键事件
  **不进 CFRunLoop 的 source**——同一个循环里一圈圈泵 `CFRunLoopRunInMode(kCFRunLoopDefaultMode, …)`
  收不到热键，`CGEventTap` 的回调却照收（所以不是「没在泵」）；`RunApplicationEventLoop()` 收得到，
  但它要阻塞到退出，塞不进「画帧 + 读键盘」。于是每轮 `ReceiveNextEvent` 只按 `kEventClassKeyboard`
  的按下 / 松开两类取值（队列里别人的事件原样留着）、`SendEventToEventTarget` 派发到 application
  event target——这正是 `RunApplicationEventLoop` 内部做的事。实测 150ms / 500ms 的泵节奏下，单次按
  与连按都不丢事件。**早期那版只泵 CFRunLoop**，于是「注册成功、日志有、按下去没反应」。

## 桌面歌词（Windows / macOS，实测 2026-10-12 / 2026-10-13）

播放时在桌面最上层浮一条「当前句 + 翻译 + 下一句」，不占终端、不抢焦点。它分成两半：**状态机**
（`overlay.rs` 平台无关的那部分，`App::tick` 每帧递一帧进去、`sync` 顺带每帧泵一次平台事件）
决定「要不要重画、画什么」，**平台实现**（`#[cfg] mod imp`：Windows 是专用线程 + 分层窗口，
macOS 是主线程 `NSPanel` + 每帧手动泵 AppKit）只管把 payload 画出来。分开的理由：状态机是纯逻辑，
能单测（12 条）；窗口那一半只能靠探针 + 真机看。

| | 做法 | 为什么 |
|---|---|---|
| 怎么浮在桌面之上 | 分层窗口（`WS_EX_LAYERED + WS_EX_TOPMOST + WS_EX_TOOLWINDOW + WS_EX_NOACTIVATE`）+ `UpdateLayeredWindow` 喂一块 32 位 DIB | 不要任务栏按钮、不抢焦点；分层窗口自带逐像素 alpha，字边缘能真的半透明 |
| 为什么不用 `SetLayeredWindowAttributes` + key 色 | 灰度抗锯齿的字边缘是**半透明**像素，取色透明只能整像素透过或不透 | 边缘会混出一圈 key 色的锯齿；逐像素 alpha 才让「描边 + 抗锯齿」都干净 |
| GDI 不写 alpha 怎么办 | 先用「白字黑底 + `ANTIALIASED_QUALITY`」把 GDI 的输出画进**第二块 DIB 当覆盖率蒙版**，再在 Rust 里按 over 合成到预乘 BGRA（`composite`） | 32 位 DIB 里 GDI 只写 RGB、alpha 保持我们清零的样子；直接画完 `UpdateLayeredWindow` 会得到一个**全透明窗口**（第一版探针就这么写废的） |
| 为什么要描边 | 8 个方向各画一遍正文（描边色），再画正文（本身颜色） | 桌面什么背景都有，纯色字总有一段看不清 |
| 鼠标怎么办 | 锁定 = `WS_EX_TRANSPARENT` + `WM_NCHITTEST` 回 `HTTRANSPARENT`；解锁 = 去掉前者、回 `HTCAPTION` | 锁定态「点不着但看得见」；解锁态让系统自己拖，`WM_EXITSIZEMOVE` 收尾 |
| 位置存哪 | **中心点**存 `desktop-lyrics.json`（独立状态文件） | 窗口宽度随文字长度变，存左上角会一行长一行短地左右抖；`config.toml` 是手写的，程序不改写它（跟 `history.json` 一个口径） |
| 锁定态 | **不持久化**，每次启动都是锁定的 | 省得下次开机「怎么点不到」；忘了锁回来才是真正的坑 |
| 空闲成本 | `App::tick` 每 150ms 递一帧，内容没变就**一个字节都不推**（`State::advance` 比 payload） | 逐帧零绘制、零分配；只有换行 / 换播放态 / 切锁定才叫醒窗口线程 |
| 尺寸与位置 | 每次重画按文本量尺寸 → 按中心点摆 → 按当前 DPI 缩放字号 | 一句话长一句话短也不会左右抖；换显示器（DPI 变）字号跟着变 |

线程模型跟全局快捷键那边是同一套：专用线程建窗口 + `GetMessageW` 消息循环；`Drop` 时
`PostMessageW(WM_CLOSE)` → `DestroyWindow` → `WM_DESTROY` → `PostQuitMessage` 再 `join`。
注册类 / 建窗口 / 起线程任一失败都降级成空句柄：状态行说一句、原因写进 `canto.log`，播放与界面照常。

### macOS：无边框 `NSPanel` + 主线程每帧泵（实测 2026-10-13）

没有第二个进程、没有窗口线程：窗口在主线程建，事件由 TUI 循环每帧拉。几件值得记住：

| | 做法 | 为什么 |
|---|---|---|
| 事件怎么来 | `App::tick` 里 `sync` → `Imp::pump`：`nextEventMatchingMask:untilDate:[NSDate distantPast] inMode:NSDefaultRunLoopMode dequeue:true` + `sendEvent:` | 没有 `NSApplicationMain`。CFRunLoop 泵不出 AppKit 的事件（同全局快捷键那节的实测），`NSApp.run()` 会阻塞到退出 |
| 窗口 | 无边框 `NSPanel`（`Borderless \| NonactivatingPanel`）+ `level = Floating`(3) + `canJoinAllSpaces + stationary + fullScreenAuxiliary` | 不抢焦点、不进 Dock、各 space 都在场；`CGWindowList` 里实测 layer=3 |
| 透明与鼠标 | `opaque=false` + `clearColor` + `hasShadow=false`；**锁定 = `ignoresMouseEvents=true`**，解锁 = `false` + `isMovableByWindowBackground` | 锁定态「点不着」；解锁后让系统自己拖窗口（探针验过合成拖动跟手、且不激活自己） |
| 文字 | 三个透明 `NSTextField` + `NSAttributedString`，描边用**负 `strokeWidth`** | 负值 = 填充 + 描边一次画完（Windows 那边是八方向各画一遍再合成）；中文 shaping 交给系统 |
| 尺寸与位置 | 每次 `push` 按文本实测尺寸重摆；中心点仍存**左上原点**，进 AppKit 按主屏高换算 | 与 Windows 同一套算法、同一个 `desktop-lyrics.json` |
| 拖动回传 | **解锁态**每帧读一次窗口矩形，跟记着的中心点比、**差过 1 点**才回传；锁定态连矩形都不量 | 拖动只发生在解锁态；`setFrame` 把原点**吸附到整点**，量回来的中心天生带 ±0.5 的舍入，拿它当「挪了」回写会累积成「每开关一次窗口往下飘一点」（见「开关两次才发现的三个坑」） |
| 字体 | 配置里的字体面认不出来（模板里那串是 Windows 字体）就回退系统字体 | 实测 `Microsoft YaHei UI` → `.AppleSystemUIFont` |
| 主屏尺寸 | `NSScreen.mainScreen` 的 frame（逻辑点） | 原来非 Windows 分支是给空实现占位的硬编码 1920×1080，拿它算默认位置会偏（实测 (960,918) vs 真实 (896,952)） |
| 失败降级 | 拿不到主线程标记 / 激活策略失败 / 建窗口失败 → 一句话 + 日志，句柄是空的 | 与 Windows 同口径：播放与界面照常 |

两个只有真机才会暴露的坑，写实现时别重踩：`Retained<T>` **不是** `repr(transparent)`（把
`&retained` 当对象指针塞进 `NSDictionary` 会段错误，必须 `&*retained`）；`setIgnoresMouseEvents`
的极性写反过一次，症状是「锁定态点得着、解锁后拖不动」。

真机验收跑在实施计划的清单里（Windows：「点不着」「拖完重启回到原位」「压在全屏 tuios 之上」
「热键关掉后窗口没了、日志里连『就绪』都没有」「状态文件写成屏外会被夹回」；macOS：另加
「窗口中心 = 主屏底部居中」「暂停按 `hide_when_paused` 藏/回」「热键开关真拆真建」
「**关掉再开连按 8 轮：窗口真下屏、再建成功、位置一点不飘**」）。

### 开关：热键真拆真建（2026-10-13）

原来「建不建」由 `[desktop_lyrics] enabled` 在启动时定；现在挪到全局热键 `lyrics`
（默认 `ctrl+shift+d`），并且**真拆真建**——关掉时窗口、线程（Windows）/ panel（macOS）都
不在，所以「关掉零成本」是物理上的，不是靠跳过 `sync` 装出来的。要点：

| | 做法 | 为什么 |
|---|---|---|
| 建 / 拆 | `toggle` → `imp::install`，或 `imp = Imp::none()`（`Drop` 收尾） | 两端本来就已经是建/拆对称的形状：Windows 的 `Drop` 投 `WM_CLOSE` 再 `join`（**同步**收回，所以再建时上一份已经彻底没了），macOS 的 `Drop` 里显式 `close()` 面板（只 release 不下屏，见下） |
| Windows 窗口类 | `RegisterClassW` 返回 0 且 `GetLastError() == ERROR_CLASS_ALREADY_EXISTS(1410)` 当成功 | 类名在进程里注册一次就够；只有真拆真建才会第二次走到这儿（以前只建一次，所以看不出来） |
| 「开没开」 | `imp::Imp::running()`：Windows 看 `hwnd != 0`、macOS 看 `inner.is_some()`、其它平台恒 `false` | 一处判断同时管住「谁算开着」和「`sync` 要不要干活」（`sync` 开头就早退，连 payload 都不造） |
| `State` 重置 | 重建时 `state = State::default()` | `State.last` 记着上一份窗口的 payload；不清的话新窗口第一帧 `advance()` 判定「没变化」→ **窗口永远空着**。顺带把锁定态带回默认（拆了再建是锁定的、点不着） |
| 位置通道 | `positions: Option<Receiver>` **收进 `DesktopLyrics`**（原来是 `App.lyrics_positions`） | 每次建窗口都新开一条通道；放 `App` 上重建后拿到的还是旧通道，拖动回传就断了 |
| 落盘 | 开关与位置在同一个文件：`{"shown":bool,"cx":int,"cy":int}`；`take_state()` 只在变过时给一份 | 开关是**状态**不是偏好（热键不该去改使用者的配置文件）。缺省 `shown = true`（= 老的 `enabled = true`）；老配置里残留的 `enabled` 只在状态文件还没记过开关时当一次初值（`start_shown`） |
| 起不来 | 通知一句 + 日志，**不落盘** | 文件记的是「你想开着」、内存记的是真相；再按一次热键就是重试 |

派发只在主界面（`Screen::Main` 或首页 `Screen::Home`——七个动作同一条规则；登录屏直接丢）；
热键**不因开关状态而注销**——关掉了还得靠它开回来。`[hotkeys]` 因此从 6 条变 7 条（`lyrics`），`enabled` 从配置模板里消失。

### 开关两次才发现的三个坑（macOS，实测 2026-10-13）

热键开了之后才会有人真的反复「关 → 开」，于是三个只在「建 → 拆 → 再建」里露头的问题浮出来。
前两个的症状合起来就是使用者报的那句「全局热键关不掉，再按一次说『歌词窗口起不来』、窗口还冻在
那儿不换词」：关的那一下窗口没真下屏（但内存里已当它没了 → 冻住），开的那一下在建面板之前就
撞在激活策略上。第三个要连按几轮才看得出来。

| 坑 | 实情（探针 / 真机） | 修法 |
|---|---|---|
| 拆窗口 | `Retained<NSPanel>` drop 只发一次 `release`；窗口上屏期间 AppKit 自己持有它，**只 release 不下屏**——`CGWindowList` 里还在（`onscreen=1`），而 `is_running()` 已是 `false` → `sync` 早退 → 窗口停在最后一句 | `Drop for Inner` 里显式 `panel.close()`；建窗口时 `setReleasedWhenClosed(false)`，把释放权只留给 Rust 的 `Retained`（免得 `close` 与它各 release 一次） |
| 再建窗口 | `NSApplication.setActivationPolicy(Accessory)` 是**幂等 setter**：第二次起返回 `false`（「没变化」，不是失败；探针 1st=1、2nd=0、3rd=0）。原来 `if !setActivationPolicy(..)` 直接当失败返回，于是每次重开都在建面板之前报「歌词窗口起不来」 | 先看 `activationPolicy()`：已经是 Accessory 就跳过；只有「想设却没设上」才算失败 |
| 位置回写 | `setFrame` 把窗口原点**吸附到整点**，量回来的中心天生差 ±0.5（`round()` 之后 ±1）。原来每次重画都拿这个测量值当新中心点写回状态文件，下一轮建窗口再从它出发——连按 8 轮实测 `cy` 961 → 972（每轮 +1~2） | 重画一律按**记着的**整数中心摆；只有**解锁态**才量矩形，且差过 1 点（吸附噪声的量级）才算拖动 |

Windows 那半不受影响：`Drop` 走 `WM_CLOSE` → `DestroyWindow`（真销毁）、类名重复注册
（`ERROR_CLASS_ALREADY_EXISTS`）早就当成功处理、窗口坐标本来就是整数像素。
真机回归（`ctrl+shift+d` 连按 8 轮 + `ctrl+shift+l` 连按 4 次 + 合成拖动 + 重启）：每轮窗口真下屏、
再建成功（日志 11 条「桌面歌词窗口已就绪」、0 条失败），`bounds` 的 `y` 与状态文件的 `cy` 全程不变，
拖动后重启回到拖到的地方。

## 曲目列表的列模型与表头（2026-10-13）

所有「装着一堆歌」的屏（收藏 / 歌单曲目 / 搜索 / 本地曲库 / 本地歌单曲目 / 历史 / 队列浮层）
共用一套列模型，实现在 `src/tui/draw/rows.rs`（纯函数：列声明 → `fit` 分宽度 → `header` /
`line` 画两行）。设计取舍（完整决策记录见 `superpowers/specs/2026-10-13-track-table-design.md`）：

- **列集按屏声明**：`track_columns()` 九列（标记 标题 歌手 **专辑** 时长 音质 体积 缓存 下载），
  `local_columns()` 去掉最后两列（本地歌不经过缓存，那两列恒空），历史加一个 `备注`
  （「时间 · 来自《来源》」），队列浮层六列（最宽 72 列，没有音质/体积/备注）。
  行数据统一由 `rows::Row` 装（填不出的那一格写占位符：`--:--` / `—`），各屏只负责把 `Row` 填满。
- **宽度分配**：定宽列永不让位（`时长 5`、`音质 8`、`体积 7`、`缓存/下载 各 4`、`标记 1`、
  列间 1 空格）；三个 `Fill` 列（标题 / 歌手 / 专辑，`min 8`）吃剩余，窗口不够时按 `DROP_ORDER`
  （`备注 → 专辑 → 体积 → 音质 → 时长 → 歌手`）撤列。**60 列下专辑自己就出局**，所以加这一列
  没动最小窗口（历史屏撤完 备注+专辑 正好 60，其余 8 列一个不少）；80 列起它出现。
  208 列实测（真机，本地那屏 7 列）：标题 5、歌手 65、专辑 124、时长 183——三列各 59 列，
  余量吃得刚好；四档（60/80/120/200 × 曲目/历史/本地）的精确宽度都钉在 `rows` 的单测里。
- **专辑那一列的数据**（2026-10-13 加）：QQ 歌单/「我喜欢」来自 `parse_song` 的 `album.name`、
  搜索来自扁平的 `albumname`、本地歌来自曲库扫描时读的 album tag（真机那三首是
  `年华` / `太阳之子` / `听！我们的歌`，与 `ffprobe` 读出来的一致）；历史只有新记录带
  （`Entry.album_name`，`serde(default)`，升级前的老条目写 `—`）。没有 album tag 的文件也是 `—`。**`fit` 拿到的宽度要减去 `INDENT`（2 列）**：`List` 渲染数据行时自己会留出
  选中符号（`▶ `）那两列，表头是普通 `Paragraph`、不会——所以 `header` 自带这两列缩进、
  `line` 不自带，谁补第二次就整体右移两列（有逐列对齐的测试钉着）。
- **表头画在列表块内部**（`Block::inner` 之后再切一行），所以 `draw::layout` 一行没动；
  可用高不足 6 行时不画（把那一行还给数据），**队列浮层例外**：它的高度是照着内容算的，
  表头那一行不多占谁的位置，所以总是画。
- **两个标记的口径**：`●` = 这份在 `~/.cache/canto`（`App.cached`，启动与升级完成时刷新），
  `↓` = 下载目录里有同名文件（`App.downloads`，启动 / 下载完 / `r` 三处刷新，key 是
  `歌手 - 标题` 这个 stem）。取值优先级 **缓存 > 下载 > 曲库 > 配置下限预估**，写在
  `rows::copy_of()` 一处——三处「列在撒谎」就是它的来龙去脉（本地 FLAC 显示 `MP3 128k`、
  已下载的看不出来、历史与本地歌单整列占位）。
- **本地歌的容器与大小**来自曲库索引本来就有的 `Entry.size` 与路径扩展名
  （`download::container_label`：`flac` → `FLAC`、`m4a` → `M4A`…），不再走档位估算。
- **历史补两个字段**（`duration_secs` / `sizes`，都 `serde(default)`）：起播那一刻手里就有，
  落盘存下来，历史屏那三列才是真的；升级前写的老记录读回来是 0 → 写占位符，从别的列表再播
  一次即补齐。本地条目按 mid 查当前曲库（文件换过就是新值），查不到才用记录里那份。
- **顺带修掉的一处**：`备注` 列的 `None` 原来退回空串、不补齐（别的每一列都会补到列宽），
  于是带备注那一行比表头短一截——是加专辑列时那条「两行一样宽」的断言把它逼出来的。
- **真机实测**（2026-10-13，macOS，208×55，未登录；加专辑列后在**独立 `HOME`** 的实例上复验过
  ——机器上那份 `~/.config/canto` 当时被另一个实例占着，隔离实例不碰使用者的数据）：
  本地曲库三首的「专辑」列是 `年华` / `太阳之子` / `听！我们的歌`，六列（标题/歌手/专辑/时长/
  音质/体积）逐列对齐按显示宽度数过全对。老记录与 60 列两档由第一层代偿（四档宽度单测）。
- **真机实测**（2026-10-13，macOS，208×55，未登录）：本地曲库两首 mp3 报 `MP3` + 真实大小
  （`4.2MB` / `3.4MB`，与磁盘一致）；临时放一个 3 秒 FLAC 进 `~/Music/canto`，`r` 之后那一行
  是 `FLAC` + `53KB`（54360 字节 ÷ 1024），删掉文件再 `r` 那行消失；播一首本地歌，历史最上面
  两条（`刚刚`）带着真时长/容器/体积，老条目同一屏并排；表头与数据逐列对齐用脚本按显示宽度
  数过（左对齐比起点、右对齐比右端，5 列全对）。
- **本轮没验到的**（这台机器未登录：`~/.config/canto` 里没有 `session.json`）：`●` 与 `↓` 的
  真机表现（要 QQ 的歌才会出现在列表里）、`d` 下载后 `↓` 立刻出现、删文件 + `r` 后 `↓` 消失、
  历史老条目的占位符（QQ 老条目未登录时不列）。这几条由第一层测试代偿：`rows.rs` 的
  「行取值四态」（缓存命中 / 下载命中 / 都没有 / 本地歌）与 `draw/mod.rs` 的
  「老条目写 `--:--`」都在跑；真机补验要先扫码登录。
- **顺手发现并修掉（收尾 commit）**：`refresh_local_view`（`state.rs:2205`）原来把刷新前的选中
  **无条件**写回 `state.select(previous)`，而它可能是 `None`（冷启动第一次进 `5`）——于是那一屏
  一行都没高亮，`Enter/a/x/d` 这些「作用于选中曲目」的键全无反应，得先按一下 `j`/`k`。改成跟
  `refresh_history_view` 一样只在 `previous` 还指得到人（`*index < view.len()`）时写回。
  实测：修前冷启动进 `5` 一个 `▶` 都没有；修后第一行有 `▶`，`Enter` 立刻起播。

## 本地曲库（`5`，阶段一，2026-10-13）

不登录、没网也能用的一半。设计取舍（完整决策记录见
`superpowers/specs/2026-10-13-local-library-design.md`）：

- **合成 mid = `local:<绝对路径>`**：`Song.mid` 是队列 / 历史 / `♪` / 歌词缓存的全链路键，
  给它一个带前缀的合成值，本地歌就**不用**在这些地方开第二条路；前缀保证永远撞不上 QQ 的
  14 位 base62。代价写在「已知限制」里：路径即身份，改名 = 新歌。
- **索引是 `~/.cache/canto/library.json`**（派生数据，删了只会重扫）：扫目录靠 `lofty` 读 tag
  与时长，`mtime`/size 没变的条目原样沿用，所以第二次起很快；`r` 是全量重扫。数据目录只放
  使用者自己建的东西（会话、历史、本地歌单），所以索引刻意放缓存目录。
- **字节来源分两支**：`Track` 的来源是 `TrackSource::Cdn(候选)` 或 `Local(路径)`——枚举而不是
  「候选 + 可选路径」，后者能造出两种都没有的非法状态。本地分支**不碰缓存也不碰网络**：直接
  `File::open` 解码（候选为空也照样能开，这条是单测钉的）。
- **歌词只在本地找**：音频同目录同名 `.lrc` → `lyrics_dir` 里的同名 `.lrc` → 内嵌歌词
  （`lofty` 的 `ItemKey::Lyrics`）。命中后照旧写进歌词缓存（key 用合成 mid），桌面歌词那套不变。
- **登录态是状态字段不是全局查询**：`App.logged_in` 启动时读一次会话，之后由登录成功 / 登出
  维护。没登录时首页**仍然画 QQ 三屏**（进去给一句「需要登录：按 L」），本地曲库与历史照进；
  `L` 的两副面孔：未登录 = 去登录屏（这时候才取二维码）、已登录 = 登出回首页且**不清队列**
  （本地歌接着放）。`start_login` 因此只有一个调用点——启动不再取码，没网时启动零请求。
- **真机实测**（2026-10-13，Windows，未登录）：进 `5` 列出 `Music\canto` 三首（时长来自 tag、
  体积列 `—`）；播一首有真歌词（来自 `canto-lyrics`）与真频谱；`canto.log` 里 HTTP 行数 **0**。
- **已知欠账（阶段一留下的）**：① 播放条的「档位」对本地文件是占位值（`MP3 128k`），要改成
  `Option<Quality>` 再渲染成「本地」；② 本地曲库屏的状态行提示仍是列表那句（含 `p 加歌单`，
  本地屏不绑 `p`）——`hints` 目前只吃 `Context`，要吃下菜单才能分岔；③ 首页 QQ 三格的未登录
  副标题（「需要登录」）没做。

## 本地歌单（`6`，阶段二，2026-10-13）

自己建的那种歌单，**放数据目录**（`~/.config/canto/local_playlists.json`）——跟索引刻意相反：
它是使用者自己建的东西，不是派生数据，删了不回来。

- **条目只存 `mid` + 标题/歌手的快照**：文件被移走或改名之后条目还在（渲染成「（已丢失）」），
  不会因为一次扫描就把歌单清空。代价：快照会跟文件里的 tag 走偏；`mid` 是 `local:<绝对路径>`，
  所以路径即身份（改名 = 新歌，跟曲库同一条）。
- **两级列表复用「在线歌单」那套**：`nav.local_shown` = 进到第几张（面包屑「本地歌单 › 名字」），
  `Enter` 进 / `Esc` 回；曲目由条目现造，**不去曲库索引里查**（文件不在了也要画出来、标一句）。
- **改一次落一次盘**（tmp + rename）：建 / 改名 / 加 / 移出 / 删整张都在动作里同步写。名字规则：
  去首尾空白、非空、不与别的歌单重名（改成自己原来的名字不算）；挡下来时输入态**留着**让人改。
- **`P` 只在「本地曲库」屏**（别的屏上选中的歌不一定有本地身份）：选择框第一行固定是「新建…」，
  选它就直接问名字、建好顺手把这首加进去；同一首加两次只留一份（说一句「已在歌单里」）。
- **`D` 是「这一屏的破坏性动作」**：历史屏清历史、本地歌单屏删整张、别的屏不做事——连按两次，
  中间按别的键就作废。代价：`Action::HistoryClear` 这个名字在本地歌单屏名不副实（按屏分岔）。
- **真机实测**（2026-10-13，Windows，`tuios`）：首页 3+3 六格；`5` 三首 → `P` 选择框第一行
  「▶ 新建…」→ `Enter` 问名字 → 打「通勤」→ 状态行「已加入：通勤（新建）」；`6` 列出「1 通勤」→
  `Enter` 进曲目 → `Esc` 回 → `R` 改名「通勤早」→ `D`「再按一次 D 删掉这张歌单」→ `D` 删掉 →
  空态「还没有本地歌单 · N 新建一张」。**进歌单后面包屑不变是实测才发现的真 bug**：`title_and_count`
  原来只看 QQ 的 `shown`，已修（`local_shown` 一起看）。未验：离线那一半（`HTTPS_PROXY` 注入不进
  `tuios` 起的窗口）。
- **已知欠账（阶段二留下的）**：① 曲库屏状态行那句提示仍写着 `p 加歌单`（本地屏不绑 `p`），与
  阶段一 ② 同源；② 本地歌单里的歌**没有时长**（条目快照只有 mid/标题/歌手），列表显示 `--:--`，
  档位列也还是曲库那个占位值；③ 歌单列表那一级的「筛选命中数」没有测试钉。

## 已知限制（细节）

- **频谱没有声卡也能验一半，另一半只能真跑**：测试用的哑引擎（`Engine::silent`）的 mixer
  没人拉样本，音频源根本不推进，所以别处的频谱恒为零。`player.rs` 里那条冒烟测试直接拉一个
  真 WAV 解码器走完整条链路（不需要声卡，能进 CI），但**「柱子跟着音乐动起来是什么样」只能
  起一次真播放用眼睛看**。
- **hi-res（192kHz）的高频段显示质量**：抽稀用滑动平均做了粗低通，16kHz 以上仍可能有轻微
  噪底。**只影响显示**，音频一个采样都没动（包装器是透传的）。
- **观感常数是本模块唯一不能靠单测定的部分**：平滑 τ（起振 0.12s / 回落 0.40s，在
  `tui/state.rs` 的 `advance_visualizer`）、dB 窗口与高频倾斜（`spectrum.rs` 顶部那几个常量）。
  觉得柱子太肉 / 太抖就改 τ，低频常年顶格就调 `DB_CEIL`。
- **缓存只收「顺序听完」的歌**：中途跳过、往回拖过的那些不进缓存（有洞的文件接不上），
  所以「第一次听某首歌」仍然完全依赖网络；网络中途抖动会卡住（没有独立读超时，
  靠 TCP 重传超时兜底）。
- **「我喜欢」只读**：界面里已没有收藏 / 取消收藏的入口（原来的 `f` 已删）。两条路都不通：
  把歌**从「我喜欢」移出**恒回 `80105`（`DelSonglist` + `dirId=201`，换 `tid`、换
  `songType`、换 `tid=0` 都一样）；**加进去**即使服务端回了成功也看不到——写完之后从不重拉
  「在线收藏」那一屏（旧实现给的是 `refresh: None`，而 `switch_menu` 只在没拉过时才拉）。
  所以收藏与取消收藏都只能去官方客户端。普通歌单的加/删都正常。
- 经典写入接口 `fcg_music_add2songdir.fcg` 现在对任何会话都回 `{"code":403,"title":"no permit"}`
  ——**与登录方式无关**（扫码会话照样拒绝），`g_tk=5381` 与按各 cookie 算的 hash33 都不行。
  写歌单走 `musicu.fcg` 的 `music.musicasset.PlaylistDetailWrite`（见 `qq/write.rs`）。
- 搜索接口不返回 hires 大小，所以搜索结果的音质标签和体积可能低估（不影响取流，候选链是固定的）。
- 列表里那一列（**格式 + 档位 + 体积**）按**配置的下限**算：配置成 128 就列 `MP3 128k 4.4MB`，
  不会列 `FLAC 31MB`，免得以为它要下无损；已缓存的那行显示缓存里那份（命中缓存时播放/下载
  用的就是它）；播放条里那个来自**实际取到那份流**的 `Content-Length`，是真在下的大小。
- **历史屏的行不显示时长与档位**：历史里只存 mid / 标题 / 歌手（够重播：取流只认 mid），
  没有的字段就不画，免得显示成假的 `00:00`。
- **同一首歌在同一列表里出现两次，两行都会标 `♪`**：标记按 mid（QQ 全局唯一）比对，
  比按「标题 — 歌手」字符串准，但重复出现的同一首无法区分。
- 「会话已失效」的判定码（`session::looks_expired`）按 401 与已知文案写就，
  **还没等来一次真实的会话过期去核对**；下次遇到时把 `--log debug` 里的响应补进去收紧。
- 下载的 `hires` 档位体积很大（单曲约 150MB）。默认档位是 **320k MP3**（约 10MB/首）；
  要无损就把 `config.toml` 的 `quality` 改成 `flac`。

## 设计要点

**界面**

- **首页判定要排在各屏分支之前**（`App::draw` 里的空子）：`go_home()` 只动 `Screen`，
  `nav.menu` 还记着上一屏——「本地曲库」那条分支（它因为扫描态 / 空库引导而单独提在 `draw_content`
  外面）只要排在首页之前，从曲库按 `Esc` 回首页时就会「状态行提示是首页那套、画面还是曲库那屏」，
  看着像 `Esc` 没反应。
- 界面只有一块内容区（标题就是「我在哪 + 有多少条」，如 `在线歌单 › 嗯 42 首`）+ 可选的两个栏
  （底部**歌词栏** `y`、**频谱区** `v`），播放条与状态行常驻。每屏各存一份列表与选中位置，
  所以「搜一下歌单就没了」不会发生。曲目列表**自己还有一行表头**（列由屏声明，让位顺序见
  「曲目列表的列模型与表头」那节），它画在列表块内部，所以「内容区 = 列表 / 频谱区」那条
  互斥规则不受影响。
- **键位映射是纯函数**（`tui/keys.rs`）：`KeyEvent` + 上下文 → `Action`，模态（帮助 /
  队列浮层 / 选择框）优先，输入态其次。这类优先级靠手点很难验证，所以用单测钉住。
- **登出（`L`）是个普通全局键**（原来只在帮助浮层里能按）：`Context::Content` 与 `Context::Home`
  各绑一次；输入态里 `L` 还是打字、模态浮层（队列 / 选择框）仍吞键——它们开着时是「一个小
  编辑器」。代价是它挨着 `l`（快进 10 秒），CapsLock 一下就登出，而登出会清掉本地会话；
  和 `Shift+D` 清队列一样，是**无确认**的破坏性键。
- **队列也是纯逻辑**（`tui/queue.rs`）：四种模式的推进、增删插的边界都在那里单测；
  「一首播完往哪走」与「按 `n` 往哪走」是两个入口（单曲循环下按 `n` 仍要前进）。
- **首页是屏幕层的第三个状态**（`Screen::Home`，跟 `Login`/`Main` 并列）：它不套 `Menu`/`Nav`
  那套「一份歌曲列表 + 选中位置 + 筛选」——首页不是列表，自己只留一份选中位置（`ListState`）。
  四格入口由 `Menu::ALL` 生成，编号就是下标 + 1，按 3 列换行（4 项 = 3 + 1）、整块在内容区
  居中，所以加一屏只要动 `Menu` 那一处。登录后落在这里（不再替使用者预取收藏），`0` 从任何
  主界面位置回首页、列表顶部再按 `Esc` 也回首页（首页自己按 `Esc` 无绑定：它是最外一层）。
  派发不另立路径：`Screen::Home | Main` 都走 `apply`，差异靠键位表 `Context::Home` 与
  `apply` 里几处屏判断。
- **浮层只盖内容区**：队列浮层与频谱区都在内容区里画，播放条与状态行永远露着
  （它们是常驻信息，被挡住就没法边看队列边看进度）。
- **`?` 帮助是一张两列表**（左键右述，说明从固定列开始，键列宽取最宽的键）。一行一个键，
  方向键跟 `j`/`k` 写在同一格（它们是同一件事的两种按法）；**屏专属段只在真有专属键时才在**
  （收藏屏没有），且排在最前——内容上限 18 行、超出就 `j`/`k`/`↑`/`↓`/`g`/`G` 滚（上限按
  浮层的实际高度在绘制时回夹），而「我在这一屏能按什么」是最常查的。
- **浮层里不写操作提示**：关闭 / 滚动 / 登出都由状态行那条提示给（`draw::hints`）——状态行
  是操作提示的唯一去处，浮层只放内容。于是浮层高度 = 内容 + 上下边框，滚动提示也不再需要
  判断「装不装得下」。
- **帮助里那一栏全局热键是现读配置的**（原来只在 README 里能查到）：组合取
  `config.hotkeys.bindings()`（它已经实现「空串 = 不注册」，于是禁用的那条自然不列），
  说明取 `hotkeys::DEFAULTS`——加一条热键只要在那张表里加一行，帮助跟着走。组合会美化
  （`ctrl+shift+right` → `Ctrl+Shift+→`），认不出的词只首字母大写；平台不注册热键
  （`hotkeys::SUPPORTED` 为假）就整栏不出现，免得许诺按不出来的键。
- **操作提示统一在底部状态行**（按当前上下文给可用键），面板标题只报「这是什么」——
  `歌词 · 歌名` 就是 `歌词 · 歌名`，不挂「按 `v` 退出」之类的话；屏特有的键在 `?` 帮助里。
- **标题是派生的**（`Nav::title_chain()`：菜单 + 是否在某个歌单里；各屏的条数在画标题时
  现算），不存成状态——存过一次就踩过坑：记录一条播放历史会把**别的屏**的标题改写成
  「历史 N 条」。
- **歌词栏**（`y` 开 / 关）：内容区底部那一条，滚动位置自己算——当前句始终落在可视区正中，
  滚到开头 / 结尾就夹住（不然会飘出整屏空行）。**没有歌词也画**：还在拉写「歌词加载中…」、
  拉完没有写「暂无歌词」。频谱区开着时它仍在最下面（两栏合起来就是今天的「大频谱」）。
- **内容区是「列表 + 两个栏」**（`y` 管歌词栏、`v` 管频谱区，两个开关**互不干扰**）：
  **频谱区与列表互斥**（开着就替掉列表），**歌词栏永远在内容区最下面**。歌词栏高
  `(内容区/3).clamp(5, 12)`；频谱区 = 内容区减歌词栏（歌词栏不占位时就是整个内容区）。
  顺序是「频谱在上、歌词在下」：频谱永远在动、歌词是要读的，动态元素放上方当氛围层，视线
  主焦点留在下半屏；这也让歌词栏与列表模式下的位置一致，按 `v` 时眼睛不用跳。
  **「模式」那一层没有了**：`Esc` 不再退频谱（要退按 `v`），换屏（`1`–`4` / `Enter` / `0`）
  顺手收掉频谱区（切屏就是离开这一屏）。列表被替掉时 `d`/`p`/`x`/`A`/`Enter` **照旧响应**
  ——没有模式，就没有「按键随视图变脸」；`/` 也一样，筛选输入行照旧占内容区顶上那一行
  （输入态不属于列表），不然打进去的字看不见。
- **键位写法**：默认小写；大写只留给「升级型能力」（如清队列 `Shift+D`）或小写已被占用的情形。
- **真频谱用的是音频线程的真实采样**：`player.rs` 在 `append` 之前把解码器包一层
  （`levels::LevelMeter`），采样原样透传给播放器，同时把**第 0 声道**抽稀后写进一份无锁
  环形缓冲（2048 个 `AtomicU32`，存 f32 的位模式——互斥锁会让音频线程被界面卡住，那是爆音）。
  界面每帧取一次窗口做 FFT，**算在界面线程**（放音频线程会拖住播放）。三步都必需：Hann 窗
  （不然两端截断的泄漏让所有柱子一起抖）、幅度归一化（不然换算成 dB 之后每段都顶格，画出来
  是一堵平墙）、**对数分频**（线性分频下 20~200Hz 挤在最左两三格、右边一大半几乎不动——
  不做这一步画出来的不是频谱仪）。窗口按**时间**（约 46ms）定义而不是固定点数：源采样率
  高于 44.1kHz 就抽稀，否则 hi-res（192kHz）下低频分辨率从 21Hz/格退到 94Hz/格；抽稀前做
  一次 N 点滑动平均，防的是 Nyquist 以上的内容折叠进可闻段。
- **`LevelMeter` 必须逐项转发 `Source` 的方法**，尤其是 `try_seek`：它的默认实现直接返回
  `NotSupported`，包装层漏掉转发，rodio 就认为整条音频不可跳转——`←`/`→` 与进度条跳转会
  **静默失效**，而播放本身完全正常，极难归因到这个包装层。`levels.rs` 里有一条单测钉住它
  （故意漏掉转发时，只有那一条会红）。
- **真机实测（2026-10-11，120×40 的终端；键位 2026-10-13 从 `Y` 改成 `v`）**：启动进「我的收藏」；
  按 `v` 画出频谱块——标题 ` 频谱 `、框里居中一句「未在播放」（此时没在播、也没歌词）；
  再按 `v` 回到列表；`?` 帮助里那两行写的是「`y` 歌词栏开 / 关」与「`v` 频谱区开 / 关」。**没在真机验的是
  有声音时的柱子起伏与「上频谱下歌词」的分栏**（要真起一次播放才会加载歌词），那部分
  只由绘制单测（`TestBackend` 逐格断言字符与颜色）与真解码器冒烟测试保证。
- 状态行**分成两段**：左边永远是当前可用键的提示，右边是一条**通知**。旧界面把两者挤在同一
  行，加载中就看不到键位提示。
- 右边是**一把槽**（`state::Notice`）：进度与一次性消息共用，后写的占位，不排队。区别只在
  「软写 / 硬写」——在飞的操作（加载、下载进度）是**软写**，槽里有刚发生的一次性消息时让位，
  等它过期再接着报；否则下载每 tick 刷新一次，刚按下的「已插队…」根本没人看得见。
- 寿命统一 `notice_seconds`（默认 4 秒；`0` = 只被下一条顶掉），过期在 `App::tick()` 里判
  ——那个 tick 本来就有（150ms），所以精度就是一个 tick，不用额外定时器。
- 列宽**固定 32 列**、按**显示宽度**截断（中文与书名号是双宽字符，按字符数留列会裁错），
  超出以省略号收尾。固定是为了不让左边的键位提示随消息长短抖动；代价是这里只能放短话，
  所以**错误只报一句，完整链条进日志**（`--log`）。
- **通知文案的约定**：`已<动作>：<对象>`（结果）或 `<动作>…`（进行中），一句话说清做了什么——
  **不带路径**（落到哪个文件、歌词在哪个目录都进日志）、**不带错误链**（一句 `error.to_string()`，
  完整链条 `tracing`）、**不重复**列表与标题里已有的东西（歌手、档位、体积、条数）。
  下载的三种结果就是这条约定的样板：`已下载：非酋` / `已从缓存复制：非酋` / `已存在：非酋`。
- 列表条数（`在线歌单 › 嗯 42 首`）挂在**内容块标题**上，不占通知位：它是「这个视图的属性」，
  不像通知那样说完就走，而且那块标题本来就挂筛选徽标。筛过之后只报命中/总数，不重复总数。
- **歌词栏只在「`y` 开着 + 有歌在放」时占位**（`(内容区/3).clamp(5, 12)` 行），不播放时不画空框；
  **有没有歌词都画**——还在拉写「歌词加载中…」、拉完没有写「暂无歌词」；矮屏（内容区 <
  `MIN_LYRIC_HEIGHT` = 20）自动不占位。

**数据链路**

- **域名感知的 cookie jar**（`cookie_store`），不是扁平 map。QQ 服务端会用
  `Set-Cookie: p_skey=` 明确清掉某个**域**上的旧凭据，扁平存储会把别的域的同名
  cookie 一起覆盖——voicefox 的扫码换 code 就栽在这上面。请求头由 reqwest 按 URL 自动拼。
- 粘贴来的 cookie 统一挂 `.qq.com` 并给 30 天过期时间。不这样做它只是**会话 cookie**，
  序列化时会被静默跳过，登录跨不了进程；`session.rs` 里有测试钉住这条。
- 扫码登录的每一跳都靠会话 jar 自动收 `Set-Cookie`；跟跳转链用的是**不自动跟随**的
  客户端（`http::client_without_redirect`）——自动跟随时 reqwest 把 302 吃掉，
  `Location` 与中间各跳（`p_skey`/`skey`）的 cookie 全丢，这正是 voicefox 当初
  「扫码成功但拿不到音乐凭证」的结构性原因。
- 所有接口的响应都经过 `qq::read_json`：`Content-Type` 不可信，且**登录失效只在这一个
  地方判定**（`session::looks_expired`），界面按错误类型切回登录屏。
- **边下边播**：`media.rs` 把 HTTP 响应做成 `Read + Seek`（rodio 的解码器要 `Seek`）。
  CDN 支持 `Accept-Ranges: bytes`，所以往回 seek 就重开一次 `Range` 请求，
  往前 seek 就近读掉——正常顺序播放只有一次请求，不落盘。
- 开流时校验**魔数**（`fLaC`/`OggS`/`ID3`/`ftyp`…）：CDN 的 `Content-Type` 不可信
  （实测 FLAC 被标成 `audio/x-ogg`、错误页标成 `audio/mpeg`），错误页正文不该被
  解码器当成音频播出去。
- 歌词走 `musicu.fcg` 的 `PlayLyricInfo`，参数里 **`crypt=0` + `qrc=0`** 时返回的是
  明文 base64 的 LRC（正文 `lyric`、翻译 `trans`）。传 `qrc=1` 会换成 QQ 自己的加密
  QRC（hex 密文），要多一整套解密——行级歌词不需要它。
- 写歌单也走 `musicu.fcg`：`AddSonglist` / `DelSonglist`，参数里 `songId` 必须是
  **数字 id**（mid 不行）。实测服务端码：`0` 成功（重复加/删同样返回 0，幂等）、
  `80092` 歌单不存在或无权、`40000` 方法不存在、`80105` 拒绝对「我喜欢」（`dirId=201`，
  `tid` 给 0）做移除——界面里现在只写个人歌单，「我喜欢」只读（见「已知限制」）。
- `--log` 传裸级别（如 `debug`）时只作用于 canto 自己，其它库保持 `warn`
  ——否则 reqwest/h2 会把每条连接、每个 HTTP/2 帧都打出来，把你的日志淹掉。

## 跨平台与发布

三平台同源，平台差异只有五处，都收在 `cfg` 里：

| 事情 | Unix | Windows |
|---|---|---|
| 单例锁 | 标准库 `File::try_lock`（落到 `flock`） | 同一个调用（落到 `LockFileEx`） |
| 本地时间（历史文案） | `libc::localtime_r` | `FileTimeToSystemTime` + `SystemTimeToTzSpecificLocalTime`（`windows-sys`） |
| 音频后端 | CoreAudio / ALSA | WASAPI（cpal 自己挑，代码里没有分支） |
| 全局快捷键 | macOS：主线程 + 每轮拉 Carbon 热键事件再派发（Linux：不注册） | 专用线程跑消息循环（`windows-sys`，见「全局快捷键」） |
| 桌面歌词 | macOS：无边框 `NSPanel` + 主线程每帧泵 AppKit；Linux：不建窗口（空实现，`[desktop_lyrics]` 整段不生效）。取词 / 状态机 / 位置状态两边共用 | 分层窗口 + 专用线程（`UpdateLayeredWindow` + 32 位 DIB，见「桌面歌词」） |

- 年内第几天（判断「昨天」）不用系统的 `tm_yday` / `wDayOfYear`：Windows 的 `SYSTEMTIME` 里根本没
  这个字段，统一从年月日自己算（闰年规则也一起测了）。
- Windows 的字节范围锁是**强制**的：正持锁时另一个句柄读不了锁文件内容，所以那边第二个实例报不出
  持有者的 pid（Unix 的 `flock` 是劝告式锁，读得到）。
- 数据目录三平台都是 `~/.config/canto`，刻意不用 `dirs::config_dir()`（macOS 会给
  `~/Library/Application Support`）。
- 测试走哑音频引擎（`Engine::silent`）：CI 上没有声卡也能跑完整测试，开发机也不会因为声卡被别的
  程序独占而挂测试。
- 发版由 `.github/workflows/release.yml` 在 tag 上编三份产物（macOS Apple Silicon、Linux x86_64、
  Windows x86_64），**先跑测试再打包**。Windows 用静态 CRT（目标机不用装 VC++ 运行库），Linux 在
  Ubuntu 22.04 上编（glibc 下限 2.35）。日常检查（clippy + 三平台测试）在 `ci.yml`。
  Intel Mac 不再出产物（GitHub 在逐步下线 `macos-*-intel` 镜像），老机型自己编。
